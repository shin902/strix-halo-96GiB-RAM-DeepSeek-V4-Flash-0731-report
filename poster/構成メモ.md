# 展示ポスターの構成案

ユーザーから共有された流れを保存したメモ。原稿HTMLへの反映は別途行う。
数値・性能評価・修正時期は構成検討時の候補であり、掲載前に測定ログや該当実装と照合する。

## 展示形式

- A3横8枚、2列×4段。左上から右へ、上段から下段へ読む。
- 左列の左端・右列の右端をそれぞれ2cm裁断し、全体を幅80 × 高さ118.8cmにする。
- 展示パネルは幅90 × 高さ180cm。左右の余白は各5cm（紙同士の隙間を含まない）。
- 白地・黒文字を基本に、余白を取る。HTML・画像・検証データは原稿を直接編集し、サイトは閲覧専用。

## 話の軸

**入るのか → 速くなるのか → 実際どうだったか**

技術の紹介を並べるのではなく、試行錯誤の順に問題解決を見せる。

> 入らない → 圧縮した → 余裕がない → 削った → 遅い → Vulkanへ切り替え → もっと速くしたい → 投機的デコード

## ユーザーが考えている大きな流れ

1. モデル、PC紹介。
2. 最初にDwarfStarでTurboQuantしてみる、REAPしてみる。
3. `strix-halo-llamacpp`を知る。「ROCmが遅い」という実感。ここでds4faにも触れてよい。
4. 投機的デコードで結構速くなるかも。バグも今月に入って直った。メモリ不足もREAPすればよいのでは。
5. ベンチ結果：Prefill、Decode、Acceptance rateのグラフを大きく見せる。
6. 実用レベルになったか。総評、ROCmでの遅さ、カーネル最適化など今後の展望、noteで扱う話。

## 原稿化するときの意図・確認事項

- 3〜6枚目は「TurboQuantとは」「REAPとは」「DSparkとは」という技術カタログにしない。各工夫の前に、何に困っていたかを示す。
- 7枚目で数字を大きく見せ、8枚目で「常用できるのか」に答える。
- REAPをtarget本体へ適用した試行と、drafterへ適用する話は分ける。
- TurboQuantは初期の試行錯誤として扱う。READMEにある正式測定条件（target KV q8_0 / draft KV q4_0）と混ぜない。
- ≈91GB、≈11／18／20数tok/s、+8GB、65K contextは要照合。GBとGiB、入力長、モデル、runtime、測定条件も確認する。
- 「今月に入ってバグが直った」は、掲載時には具体的な年月・修正内容・参照先へ置き換える。
- 「日本語性能崩壊」「ROCmが遅い」は、出力例や比較条件で裏付ける。ユーザーの率直な実感は構成意図として残し、展示での表現は原稿化時に調整する。
